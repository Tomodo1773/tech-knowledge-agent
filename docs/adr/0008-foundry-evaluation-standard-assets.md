# ADR 0008: 評価をFoundryの標準資産へ載せ、japaneastに留まる

Status: Accepted

## Context

評価はFoundryのバッチ評価で回っており、デプロイ済みのAgentを対象に実行して採点している。しかし標準で用意されている評価機能のうち使っているのは一部で、採点器は自作の2つだけ、質問セットは実行の呼び出しへ直接埋め込んでいる。質問セットも採点器もプロジェクトの資産になっておらず、版の管理も、画面からの起動も、run同士の比較もその先にある。

標準機能を実機で一通り動かして測った。検索結果の使い方を見る評価器が、回答が取得した記事に裏付けのない主張を付け足していることを3件中3件で検出した。これは「記事に無いことを混ぜない」というこのAgentの中心要件そのもので、自作の2つは素通りさせていた（回答内容は10件中6件合格、出典照合は10件中10件合格）。根拠性の評価器も、照合対象を明示しない設定では同じ回答を満点で通した。

このプロジェクトの目的の半分はAzureの最新AI資産を実地で学ぶことであり、標準機能を学習価値やコストで取捨選択しない。

リージョン制約も実機のエラーと公式のリージョン表の両方で確認した。japaneastはバッチ評価と、合成データ生成およびトレースからのデータセット生成に対応する。安全性評価器一式（暴力、性的、自傷、憎悪、間接プロンプトインジェクション、コード脆弱性、根拠のない属性推定）は非対応で、実行時に全行がエラーになる。レッドチームはEast US 2とNorth Central USのみ。

## Decision

質問セットをプロジェクトのデータセットとして登録し、実行はそれを参照する。版は内容のハッシュで決める。手元に状態を持たずに決まり、同じ内容の再登録で版が増えない。採点基準の指紋と同じ発想を揃えるためでもある。

自作の採点基準をプロジェクトの評価器カタログへ登録する。登録はスクリプトで行い、採点基準ファイルを正本として、登録済みと差があるときだけ新しい版を作る。

組み込み評価器を併用する。自作の2つは捨てない。組み込みはAgentとしての妥当さを測り、自作はこのプロジェクト固有の正しさを測る。「自分の記事だけを根拠にする」「該当記事が無いときは無いと言える」は組み込みでは測れないため、置き換えではなく併用とする。

ツール評価器へ渡すツール定義はデータセットの項目として供給する。Agentを対象とする設定のツール説明として渡す経路では実行時に届かず、全行がエラーになることを実測した。定義そのものは1箇所に持ち、登録時に各行へ流し込む。

run同士の比較を標準機能に任せる。同じ枠に属するrunのあいだで平均、標準偏差、差分、p値、変化の有無が返る。人が表を見比べる作業を置き換える。

トレース評価を通すため、プロジェクトのマネージドIDへApp InsightsのMonitoring Readerと、Log AnalyticsワークスペースのLog Analytics Readerを付与する。既に付与しているLog Analytics Data Readerは要求されているものとは別物で、導入時に用途が記録されていない。外すのは根拠のない変更になるため今回は残し、棚卸しは別に扱う。

本番の会話を対象にした評価と、記録から質問セットを作る経路は、人が回すときだけ動かす。定期実行と、応答ごとの継続評価は使わない。採点1件ごとに判定modelが動くため費用が流量に比例し、放置すると増え続ける。継続評価には採点する割合と1時間あたりの上限という栓があるが、単一利用者のこの規模では、栓を調整して見張る手間のほうが得るものより大きい。代償として、品質の劣化に気づくのは人が回したときだけになる。

japaneastに留まる。移設で得られるのは安全性評価器とレッドチームだけで、両者を同時に満たすリージョンが存在しない。索引の張り直しとモデル配置の再確認という代償に対して得るものが釣り合わない。安全性評価が必要になった時点では、移設ではなく、回答の組を別リージョンの評価専用プロジェクトへ渡して採点する形を先に検討する。レッドチームはAgent本体を呼ぶ必要があるためその形では手に入らず、その時点で改めて判断する。

採点基準の指紋で評価の枠を分ける仕組みは標準機能へ寄せない。同等の機能がなく、寄せると採点基準を変えたrunが同じ枠に混ざる。

## Consequences

質問セットの形式が変わり、ツール定義の項目が増える。契約と形式検査も連動して変わる。形式検査はAzureへ触らないため、CIへ入れて検証の正本に載せる。

評価器ごとに尺度が違う（0から1、1から5、その他）。結果表示の桁揃えが必要になる。

採点理由は組み込み評価器だけが返す。自作採点器はカタログへ登録しても理由の欄が空のままであることを実測した。理由を掘り出す処理は自作の分だけ残る。

ポータルの作成画面から同じ評価を組めるようになる代わりに、質問セットがストレージへ置かれる。埋め込みにしてストレージを避けたADR以前の判断を取り消す。

安全性の検証は評価の経路では行えない。検索結果を信用しない指示を入れているが、その効きを間接プロンプトインジェクション検出で測ることはこの構成では不可能で、検証手段は別に考える必要が残る。
