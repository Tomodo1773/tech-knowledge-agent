# 品質と観測

この文書は、MVPのcontent記録、Hosted Agentの評価設計と、MVP後の品質施策の正本である。何をどのsignalで記録するかの設計は[telemetry.md](telemetry.md)を正とする。

## Content記録と保護

個人利用のMVPでは、Agent versionとFunction Appの両方で環境変数`OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`を固定で`true`にし、built-in traceの質問・回答・tool入出力をApplication Insightsへ保存する。二箇所に置くのは、記録される内容が重ならないためである。Agent側のspanが持つのはtoolの入出力（`gen_ai.tool.call.arguments`、`gen_ai.tool.call.result`）だけで、質問文と最終回答はFunction側の`responses` spanの`gen_ai.input.messages` / `gen_ai.output.messages`にしか現れない。値は`true`固定とする。公式手順にある`SPAN_AND_EVENT`は別の実装向けの値で、`AIProjectInstrumentor`は`"true"`以外をすべて偽として扱う。

公開可能な技術記事と個人の技術質問だけを入力する前提であり、credential、個人情報、業務上の非公開情報はSlack質問にも記事にも含めない。これはbuilt-in `gen_ai` telemetryの設定であり、custom spanの属性・引数・戻り値を安全にするものではない。Hosted Agentの外側のResponses protocolが質問・回答と会話履歴をFoundry側で管理する一方、Agent内部のmodel callは`store: false`とし、model layerへ重複保存しない。

Slack Signing Secret、Bot token、Authorization header、event本文全文をcustom spanへ記録しない。Slack workspace、user、channel、threadの識別が必要なら[architecture.md](architecture.md#会話履歴)と同じ組み合わせをハッシュ化して使う。閲覧権限は自分のEntra IDと実行に必要なManaged Identityへ限定し、第三者OTLP backendへcontentを送信しない。保持期間とdaily capで保存費用を制御する。

## 評価設計

Hosted Agentの品質は、Microsoft Foundryのbatch evaluationで測る。評価runと行ごとの結果はFoundryのEvaluations画面に残る。この節がその設計の正本である。

### 測定の単位

**測定の単位は利用者から見える回答とする。内部部品を単体で測らない。**

検索が正解記事を引けているかは、Agentを介さず検索だけを直接叩いても測れるが、採らない。利用者に届くのは回答であり、検索が当たっていても回答が外れていれば品質は落ちている。部品単位の測定は実装へ張り付くため、実装を変えるたびに評価も壊れる。

原因の切り分けは評価器では行わず、[telemetry.md](telemetry.md#trace)のtraceで行う。質問・回答・tool入出力はApplication Insightsへ保存済みで、切り分けの手段は評価とは別に確保されている。

### 評価軸と判定器

観点は6つ、判定器は5つとする。

| 観点 | 判定器 | judge model |
|---|---|---|
| 回答の内容が期待と合っているか | ① 自作の採点prompt | 要 |
| 根拠が無いとき、無いと言えるか | ①（期待する振る舞いで書き分ける） | 要 |
| 引いた記事に無いことを混ぜていないか | ② built-in（根拠への忠実さ） | 要 |
| 指示したruleを守っているか | ③ built-in（指示への追従） | 要 |
| 検索を適切に呼んでいるか | ④ built-in（tool呼び出し） | 要 |
| 正解記事をsourceとして挙げたか | ⑤ 決定的な文字列照合 | 不要 |

観点が6で判定器が5なのは、「根拠が無いと言えるか」を独立した判定器にせず①へ吸収させるためである。合否の向きが逆のcaseを同じ器で扱えるので、評価を2本に分けずに済む。

①はAzure OpenAI graderの`score_model`で作る。promptとしきい値はrepository内のファイルへ置き、gitで追える状態にする。評価器をFoundry側のcatalogへ登録する経路は採らない。管理場所が分かれるためである。

**①のpromptへ出力形式を書かない。** 判定と理由という出力contractはFoundry側が強制的に付け足す。promptに独自の出力形式を書くと衝突して壊れる。書くのは観点だけとする。

⑤はjudge modelを使わない決定的判定であり無料だが、指示への追従の代理指標として実際に機能する。2026-08-14の実測では、10問中1問がsource blockを丸ごと欠落させた。回答の内容は正しく、その記事にしかない事実を書いていながら、出力形式だけを守らなかった。

**①と⑤を並べることがこの設計の核である。** 同じ実測で、①なら合格・⑤なら不合格という組み合わせが実際に出た。この組み合わせが出た時点で「内容は正しいがsourceの付け方が壊れている」と結果表だけで断定でき、traceを開く必要がない。単一の信号ではこの切り分けができない。

⑤の判定は「正解記事が含まれているか」だけとし、余計な記事が混ざっていないかは見ない。同じ実測で2件のsourceを挙げた回答があり、2本目も回答が実際に触れた論点の記事だった。厳しくすると偽の不合格を生む。

### 評価データセット

14件とする。

| 種類 | 件数 |
|---|---|
| 既存の問題 | 10 |
| 根拠なし | 2 |
| 複数記事にまたがる | 2 |
| 合計 | 14 |

各caseが持つ項目は、質問文、期待する振る舞い、期待するsource記事、問題の種類の4つとする。

**期待する振る舞いを全caseへ持たせる。** これが①の入力であり、欠けると①が判定できない。根拠なしのcaseでは、ここへ「該当記事が無いと述べ、推測で答えないこと」と書く。

期待する振る舞いは、実際の記事の中身に照らして書く。質問文だけから書くと、記事に固有の見解や具体的な数値を含まない一般論の回答も合格になってしまう。⑤へ渡すときは期待するsource記事の1本目だけを取り出す。決定的な文字列照合は一度に1本しか比べられないためである。

新しい種類を2件ずつにしたのは、1件だと結果がぶれたときに、その種類が壊れているのか個別のcaseがたまたま落ちたのかを区別できないためである。3件以上にしないのは、根拠なしのcaseが、将来その話題の記事を書いた時点で無効化する借金を抱えるためで、増やすほど手入れが要る。

### 実行と管理

| | 役割 |
|---|---|
| repository内のファイル | 正本。質問リスト、期待する振る舞い、①のpromptとしきい値、評価の設定 |
| コマンド | 実行と、結果の読み取り。測りたくなったら叩く |
| Foundry portal | runが残っていることの確認と、履歴の一覧 |

**結果はコマンドで読む。portalの要約だけでは足りない。** portalのレポートは判定器ごとの合格率しか出さない。合格・不合格の件数も、どのcaseがなぜその点になったかも出ない。さらにAPIの`reason`は常に空で、判定modelが書いた採点理由は判定器のsampleの中にJSON文字列として埋まっている。実行scriptはそこから理由を取り出し、不合格のcaseについて論点ごとに表示する。過去のrunも`--show`で読み直せる。

Foundryの評価はARMのresourceではないためBicepで管理できず、`azd provision`の対象にもならない。data-plane APIで作る対象であり、宣言と実体は一致しない。実行するたびにcloud側へ積み上がる。

採点基準を固定したまま実行を重ねれば比較できる。**採点基準を変えるときは評価の枠を作り直す。** 評価の枠はデータの形と判定器を抱えており、runがぶら下がったあとは編集できないためである。実装では、判定器の定義・①のprompt・しきい値・判定modelの名前から短い指紋を計算し、指紋を枠のmetadataへ書く。同じ指紋の枠があれば再利用し、無ければ作る。採点基準を変えたときだけ自動的に枠が分かれるので、基準の違うrunが同じ枠に混ざらない。質問リストは実行のたびに渡すため、caseの追加は枠を作り直さずに済むが、件数が変われば数値は動く。

`azd`にはagent評価用のコマンドが付属するが、採らない。その設定ファイルが受け付ける判定器はMicrosoftの作り置き評価器の名前だけで、①の自作promptも⑤の文字列照合も書けない。加えて質問リストをprojectのデータ資産としてアップロードする前提であり、storage不要という前提を崩す。結果の一覧と詳細表示にだけ使う。

CI/CDへは組み込まない。評価をdeployを止める品質gateにしない方針は維持する。この評価が答えるのは「壊れていないか」ではなく「良くなったか」であり、後者は前回と見比べないと意味が出ない。Agentのinstructionsやtool定義を変えたときに手で回す。

Agentを呼んでいた既存のsmoke evaluation scriptは廃止し、質問リストの契約を持つmoduleと、それを呼ぶだけの書式検査scriptへ分ける。検査するのは、質問文が空でないこと、期待する振る舞いが空でないこと、問題の種類が既定値のいずれかであること、通常caseが期待するsourceを持つこと、根拠なしcaseが期待するsourceを持たないこと、複数記事caseが2本以上を持つこと、case idが重複しないことである。最後から2つ目は設計時に数えていなかったが、これが無いと複数記事caseの種類が名前だけになるため足した。契約はunit testが実際の質問リストで確かめており、[platform-and-operations.md](platform-and-operations.md#ローカル開発)のローカル検証一式に含まれる。

### 段階

| 段階 | 件数 | 判定器 | 状態 |
|---|---|---|---|
| 1 | 10 | ①⑤ | 完了。2026-08-14に基準値を取った |
| 2 | 14 | ①⑤ | 未着手 |
| 3 | 14 | ①〜⑤ | 未着手 |

段階1の判定器を1つに絞らないのは、①と⑤の切り分けがこの設計の核であり、核を最初に確かめないと段階1の意味が薄いためである。⑤はjudge modelを使わないので①とは失敗要因が独立しており、原因の切り分けは保てる。

**段階1の基準値（2026-08-14）。** ①は10件中8件合格。5点が5件、4点が3件、3点が2件。⑤は10件中10件合格。3点だった2件は、いずれも記事にある具体を落としたことによる。1件はSocket Firewallの導入の手軽さに触れず、もう1件は作られるコンテナを3つのうち2つしか挙げなかった。どちらも判定modelのぶれではなく実際の欠落であり、しきい値4はこの粒度で機能している。

### 制約

**region.** 東日本はbatch evaluationとdata generationに対応する。risk / safety evaluatorsとagent playground evaluationsは非対応であり、この設計では使わない。

**RBAC.** 実行者にはFoundry Userが要り、deployerが持つFoundry Project Managerで足りる。projectのManaged IdentityへのFoundry User付与は評価runの失敗を防ぐために必要で、`infra/app/foundry.bicep`で付与済みである。

**dataset.** agent targetのrunは質問リストをAPI呼び出しへ直接埋め込めるため、storage accountの追加接続は要らない。

**判定modelのrate limit.** 評価は全caseを並行に走らせるため、Agent自身のmodel呼び出しと判定modelの呼び出しが同時に集中する。**Agentと判定器は同じmodel deploymentを共有している。** 2026-08-14の実測では、capacity 10（10K TPM）だと2回とも10件中3件の①が429で採点されず、点数0・不合格として残った。採点の質とは無関係な失敗である。capacityを100へ上げたところ10件すべてが採点された。GlobalStandardのcapacityは課金額ではなく速度の上限なので継続課金は増えないが、事故時に消費しうる量の上限も同時に上がる。件数を14へ増やし判定器を5つにする段階3では、同じ理由でさらに詰まる可能性がある。

**採点できなかった行の扱い。** 採点できなかった判定器は点数0・不合格として返るが、**run全体の集計ではその行が合格側に数えられる。** 集計のerrored件数も0のままである。上の実測では、10件中3件が採点されていないのに全体は9件合格と表示された。実行scriptは行ごとの結果からこれを検出し、採点できなかった件数と理由を別に出す。全体の集計だけを見て判断しない。

**コスト.** 14件 × judgeを使う判定器4つでjudge呼び出しが56回、加えてAgent自身が14回動く。2026-08-14の実測では回答1件が数百〜1,500 tokenだった。実行1回あたり20万〜30万tokenを見込む。evaluation、dataset、run履歴の保存費用は無視できる。継続課金は増えない。

### 未解決

**根拠なしcaseへの⑤の適用。** 根拠なしのcaseは期待するsourceを持たないため、⑤の比較対象が空になる。2026-08-14に切り出して確かめたところ、比較対象が空のとき⑤は**無条件に合格**する。放置すると集計上は14件中14件合格に見える。段階2で必ず踏むため、そこで対象から外すか、集計時に割り引くかを決める。複数記事caseの2本目も同じ形の問題で、⑤は1本しか比べられないため、同時に決める。

**期待する振る舞いの粒度。** 段階1の基準値で3点だった2件は、どちらも期待する振る舞いに並べた論点のうち1つを落としたことによる。論点を多く書くほど基準は厳しくなり、Agentを変えていなくても期待文の書き方で数値が動く。期待文を書き足すときは、基準値との比較が切れることを承知のうえで行う。判定器を変えないかぎり評価の枠は作り直されないため、この変化は指紋には表れない。

**instructionsと実際の振る舞いのずれ。** instructionsは「toolが返したsource blockを付けろ」と書いているが、実際のモデルは「回答の根拠として使った記事だけを選んで付ける」を行い、かつ10問中1問で丸ごと欠落させた。前者は望ましい振る舞いだがそう指示したものではなく、後者は明確な指示違反である。仕様化されていない振る舞いの上へ評価を乗せると、model差し替え時に実装を変えていないのに評価が崩れる。instructionsを実際の望ましい振る舞いへ明文化する作業は、評価を入れる作業とは分けて扱う。

## 運用指標

初期に観察する指標は、Slack eventの3秒以内2xx率、`http_timeout`による再送件数、GitHub同期・Function・Agent・Slack送信の失敗率、Agent・vector検索・end-to-endの時間、最終同期時刻、検索結果なし率、引用付き回答率、token / RU / telemetry取り込み量である。数値thresholdは実測後に定める。

## MVP後

production trace evaluation、recurring / continuous evaluation、prompt最適化、評価結果のversion管理はMVP後に検討する。これらにはpreview機能を含むため、導入時に運用負荷と価値を再評価する。必要なRBACは[architecture.md](architecture.md#hosted-agentとidentityrbac)を正とする。
